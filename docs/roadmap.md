## 現在の状態: 設計比較支援ワークスペースへの再編（0.2.0-alpha.1）

2026年8月、計算ロジックそのものは変えずに、単発セッションの計算機を
`Project → Alternative → Case → Scenario → Run` というローカルファーストの設計比較支援ワークスペース
へ再編した。詳細な設計は [`docs/design-workspace.md`](./design-workspace.md)、パッケージ構成・
技術スタックは [`docs/architecture.md`](./architecture.md) を参照。作業は5段階のタスクに分かれる。

| タスク | 内容 |
|---|---|
| Task 1 | 正準スキーマ・型・Case ライフサイクル（`@open-waterhammer/contracts`） |
| Task 2 | WorkspaceRepository・決定性 `.owhproj` バンドル・レガシー移行（`@open-waterhammer/workspace`） |
| Task 3 | 共通計算実行境界・Python production 経路・ローカル CLI `owh`（`@open-waterhammer/runner` / `@open-waterhammer/cli`） |
| Task 4 | ワークスペース UI 全体・GIS・比較・帳票（旧計算機シェルの置き換え） |
| Task 5 | リリース統合・ドキュメント・CI・警告解消 |

以下の「実装済み」「既知の制約」は、この再編後も物理・数値計算そのものとしては有効である（式・手法は
変わっていない。計算実装は `packages/core-py`（Python）に一本化された）。ただし到達経路は旧来の
単一計算機画面ではなく、新しいワークスペース UI の Analysis / Results / Reports タブ経由になって
いる。

## 既知の制約・適用と限界

要旨「§4 適用条件および評価方法」で示した範囲。再編後の実装でも解消していない項目。

### 1. 柱分離（カラム分離）未対応 🟡
- **現状**: MOC 各 BC で `H = max(CP, 0)` のクランプを行う。蒸気キャビティ形成・収縮・再衝突は未モデル化。
- **影響**: Hmax 算定は妥当だが、Hmin 側の post-vacuum 動力学は対象外。再編後に追加した防護設備比較
  機能（`transient_protection_device`）でも同様で、シードされたサンプルの防護後計算は正当に
  hmin ≈ −8.49 m という負圧を示す——これはバグではなく本項の限界の直接的な現れである
  （詳細は [`docs/design-workspace.md`](./design-workspace.md) §8「防護設備（Protection Devices）の
  意味論」）。
- **検出**: `Hmin < 0` の区間は柱分離発生のシグナル。設計実務では吸気弁・防護工で物理的に回避する前提。
- **将来対応**: 実務需要があれば DVCM (Discrete Vapor Cavity Model) または DGCM (Discrete Gas Cavity Model) を実装。

### 2. ポンプ4象限特性の簡易モデル 🟡
- **現状**: H-Q放物線 + 相似則トルクの簡易モデル。
- **限界**: 完全な逆流・逆転を含む詳細過渡解析は精度劣化。
- **将来対応**: Suter 曲線データ入力 BC を追加（実機試験データから WH/(α²+v²)・WB/(α²+v²) vs θ を読み込み）。

### 3. ループ管路網の定常計算（自前実装） 🟢
- **現状**: 自前実装は樹枝状（ループなし）のみ対応。
- **回避策**: EPANET エンジン（`steady_network_epanet`）を選択するとループ網も解ける（Newton-Raphson 反復）。

### 4. 開水路・自由水面流れ 🔴
- **現状**: 対象外（管水路のみ）。
- **将来対応**: 別プロジェクトとしての拡張可能性あり。

### 5. 自動評価は3種別のみ 🟡（再編で判明・明示）
- **現状**: `judge_design_pressure` による自動評価は `joukowsky_allievi` / `empirical_pressure` /
  `longitudinal_hydraulics` の3種別（許容圧力を入力した場合のみ）に限られる。MOC系4種別
  （単管路/管路網/ポンプ/防護設備の過渡解析）は自動評価の対象外（`needs_review`）のまま——旧実装にも
  対応する判定は存在しなかったため、今回の再編でも新規追加していない。
- **将来対応**: MOC 系の判定基準（許容圧力に加え、負圧・柱分離シグナルとの組み合わせ判定など）は
  実務要件が固まった段階で検討する。

### 本リリースでは意図的に対象外としている事項

Global Constraints（[`docs/design-workspace.md`](./design-workspace.md)）により、本リリース
（0.2.0-alpha.1）では次を明示的にスコープ外としている。実装が漏れているのではなく、意思決定として
先送りしている——将来のリリースを検討する際の公開トラッキング項目として記録する。

| 項目 | 内容 |
|---|---|
| クラウドバックエンド・公開 HTTP API | ローカルファースト（IndexedDB / `.owhproj`）を維持し、サーバー実行環境を持たない |
| 認証・コラボレーション機能 | アカウント・共同編集・アクセス制御は対象外 |
| 電子署名・人間による承認（Decision / Approval）記録 | 自動評価のみで、人が承認した記録という概念は本リリースに存在しない |
| 追加の Level 2/3 V&V ベンチマークプログラム | 参照例・実務比較検証の拡充は次リリース以降で検討（現状は [`docs/validation-plan.md`](./validation-plan.md) を参照） |

## アーキテクチャ進化のメモ

### 設計比較支援ワークスペースへの再編 (2026-08, Task 1-5 完了)
- 詳細は本ファイル冒頭「現在の状態」および [`docs/design-workspace.md`](./design-workspace.md)。

### Python 移行 (2026-05-01決定 → Stage 5b 完了)
- TS core → Python core へ計算実装を移行
- 単一の真理源を `packages/core-py/` に確立
- ブラウザでは Pyodide 経由で同じ `.py` を実行
- 既存テスト 178件の数値一致を保証して移行完了

### EPANET 統合 (Stage 6 完了)
- 定常網計算を `epanet-js` (米国 EPA EPANET の WASM 移植, MIT) に委譲
- 自前実装と数値一致を検証
- ユーザーは UI でエンジン選択可能

### 計算ライブラリ層 (Stage 7 完了、ルーティングは再編で更新)
- 全15式のメタデータを `formulaCatalog.ts` に集約
- LibraryPage で数式・入出力・GitHub link を一覧
- 各 Calculator の結果から該当式へワンクリック導線
- ルートは `#/docs/library?topic=<式ID>`（再編後の HashRouter 経路）。旧来の
  `公開URL/#joukowsky` のような単発アンカー引用 URL も、`resolveLegacyHash` が
  `history.replaceState` で自動的に新ルートへ書き換えるため、外部から引用済みの URL は無効化
  されない（ブラウザの「戻る」操作がリダイレクトを再生し続けるトラップにならないよう配慮済み）。

### Marimo notebook (Stage 8 完了、再編の影響なし)
- 学習用・検算用の対話的 notebook を3本公開
- GitHub Actions CI で自動ビルドして Pages に併置
